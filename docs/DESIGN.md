# 설계: 헤드유닛 서스펜션 모드 자동 전환 (A안)

기준: 2026-11-15. 사용자가 A안을 골랐다. 아직 코드는 없고, 차량에 보낸 명령도 없다.

## 할 수 있는 것 / 없는 것

- 할 수 있는 것(동작이 확인되면): 속도와 코너(횡가속도)에 따라 서스펜션 **단계**를 자동으로 바꾼다.
- 할 수 없는 것: 퍼센트 단위 조절, 앞뒤 따로 조절. 헤드유닛에 그런 통로가 없다([FEASIBILITY.md](FEASIBILITY.md)).

## PC 분석으로 알아낸 것

헤드유닛 프레임워크(`com.hkmc.micom.SystemService`, 디스어셈블리 근거)

- `setIndividualDriveMode(int device, int mode)` → 마이컴 패킷 `SYS_INDIVIDUAL_DRVICE_MODE_SET_C_REQ`(0x13e), 내용은 `[device, mode]` 2바이트.
  이름과 구조로 보아 커스텀 모드의 "항목별 설정"(파워트레인/스티어링/서스펜션 등)을 바꾸는 함수다.
- 호출하면 로그에 `[SystemService.setIndividualDriveMode] device: X, mode: Y, called by <pid>`가 찍힌다.
  → **순정 설정 화면에서 서스펜션 항목을 한 번 바꾸는 것을 로그로 보면 X, Y 값을 읽기 전용으로 알 수 있다.**
- 현재 상태는 `getIndividualDriveMode()`의 `DriveMode`(항목별 켜짐 상태·고장 상태·피드백 배열 포함)와 `SYS_DRIVE_MODE_DATA_M_RESP`로 돌아온다.
- 실차 로그(2026-11-08)에서 헤드유닛의 한 앱이 `getIndividualDriveMode`를 실제로 호출하고 있다. 즉 이 기능 계열은 K8에서 살아 있다.
- 순정 설정 앱 패키지 `com.hkmc.software.vehiclesetting`이 차에 설치돼 있다.

아직 모르는 것(현장 확인 필요)

1. K8 커스텀 모드 화면에 서스펜션 항목이 있는지, 선택지가 무엇인지(노멀/스포츠 2단계인지, 스마트 포함 3단계인지).
2. 서스펜션의 `device` 번호와 각 단계의 `mode` 번호.
3. 드라이브 모드가 **커스텀일 때만** 항목 설정이 적용되는지(그럴 가능성이 높다). 커스텀은 재시동하면 풀린다(취급설명서).
4. 주행 중 변경이 허용되는지, 계기판에 팝업이 뜨는지, 바꾼 뒤 실제 감쇠 변화까지 걸리는 시간.
5. NEMESIS 모듈(셸 권한)에서 이 Binder 호출이 권한 문제 없이 되는지.

1번에서 서스펜션 항목이 **없으면** 이 설계는 "드라이브 모드 전체를 스포츠↔컴포트로 전환"으로 바뀌고(가속 반응·핸들 무게도 같이 변함),
그 가치는 사용자가 다시 판단해야 한다.

## N 모드 데이터 채널 (2026-11-15 추가)

사용자 지적: N 모드 차량은 헤드유닛에서 횡G·RPM 등을 볼 수 있다. K8 프레임워크에도 같은 통로가 들어 있다.

- 요청: `SystemService.requestNModeData(int mode)` → 마이컴 패킷 `SYS_N_MODE_DATA_C_REQ`(0x141).
- 수신: `SYS_G_FORCE_DATA_M_REQ`(0x8143, `onGForceDataReceived`), `SYS_POWER_TORQUE_TURBOBOOST_M_REQ`(0x8144),
  `SYS_OIL_COOLANT_TEMP_M_RESP`(0x8178), 랩타임·성능 옵션 등.
- K8 실주행 로그(11-08)에는 이 수신 줄이 **없다**. 요청하는 순정 화면이 K8에 없어서일 수 있고, K8 마이컴이 지원하지 않아서일 수도 있다. 요청을 한 번 보내 봐야 안다.
- 이 통로는 **읽기**다. 감쇠력 퍼센트를 정하는 통로가 아니므로 A안의 한계(단계 전환만)는 그대로다.
- 되면 얻는 것: 코너 감지를 휴대폰 센서 대신 **차량 횡G**로 한다 → 휴대폰 없이 차량 모듈만으로 속도·코너 규칙이 모두 동작하고, 지연과 거치 문제가 없어진다.
- 요청 자체는 차량 제어가 아니라 "데이터를 보내 달라"는 신호지만 마이컴 송신이므로 **사용자 승인 후 정차 상태에서** 시험한다(현장 4번과 같이).

### 추가 분석 (같은 날, PC만)

순정 차량 설정 앱(`k8-ambient-sync/private/oem-vehiclesettings`, odex 분해라 일부 코드는 깨져 있음)에서:

- 커스텀 항목 번호(`DriveModeUtils`의 키→번호 변환): `DriveMode_powerTrain`=0(추정), **`DriveMode_suspension`=1**,
  `DriveMode_steeringWheel`=2, `DriveMode_awd`=3, `DriveMode_esc`=6. 화면 내부 번호일 수 있어 통신 값과 같은지는 로그로 확인한다.
- 설정 앱이 보내는 길은 두 가지다. 둘 다 `[항목, 값]` 2바이트이고 둘 다 호출 시 로그가 남는다.
  - `bO(item, val)` → `NModeManager` 경유(= `setIndividualDriveMode`로 추정, 패킷 0x13e)
  - `bP(item, val)` → `requestDriveCustomMode2([item, val])`(패킷 0x187, 로그 `[SystemService.requestDriveCustomMode2] data: ..`)
  - K8이 어느 쪽을 쓰는지는 차종 분기(`isSupportDrivemodeType2` 등)에 달려 있어 현장 로그로 정한다.
- 값(노멀/스포츠 등)의 숫자는 깨진 코드라 PC에서 확정하지 못했다.

N 모드 데이터 요청
- `requestNModeData(int mode)`는 `mode` 1바이트만 보낸다(Binder 트랜잭션 0x32, 서비스 이름은 `com.hkmc.Service.SYSTEM_SERVICE`).
- 시작/중지 값의 이름표는 프레임워크에 없다(N 화면 앱이 K8에 설치돼 있지 않음). 같은 계열 `requestNModeZeroSpeed`는 1=시작, 0=중지다.
  → 시험은 1을 보내고 응답을 본 뒤 0을 보내는 순서. **0으로 멈추지 않을 수 있고, 그 경우 시동을 끌 때까지 데이터가 계속 들어온다**(로그가 늘어날 뿐 차량 동작에는 영향 없음으로 판단하지만 확인된 사실은 아니다).
- 응답은 `SYS_G_FORCE_DATA_M_REQ: <바이트들>`로 로그에 찍히므로 오는지 안 오는지 바로 보인다. 바이트 의미(횡/종 G, 단위)는 받아 봐야 해석한다.

## 구조

```
휴대폰 앱 ──(블루투스 RFCOMM, 설정·횡가속도)──▶ 차량 모듈(NEMESIS) ──(Binder)──▶ SystemService ──▶ 마이컴 ──▶ ECS ECU
                                              ▲ 속도·주차·모드: 헤드유닛 로그(읽기)
```

- **차량 모듈**(k8-ambient-sync의 `car-relay`와 같은 방식: API 19 DEX, `app_process`)
  - 속도·주차·현재 모드는 지금처럼 로그에서 읽는다.
  - 판단은 차량 모듈이 한다. 휴대폰이 끊겨도 속도 규칙은 계속 동작하고, 코너 규칙만 멈춘다.
  - 명령은 `setIndividualDriveMode` 하나만 보낸다. 다른 Binder·CAN 호출은 없다.
- **휴대폰 앱**
  - 규칙 편집: 속도 구간별 단계, 코너 민감도, 최소 유지 시간.
  - 코너 감지: 가속도계 횡가속도(거치 방향 자동 보정, 저역 필터). 차량 모듈로 초당 10~20회 전송.
  - 상태 표시: 현재 단계, 마지막 전환 이유, 연결 상태. "자동 끄기" 버튼.

## 전환 규칙(초안)

- 속도: 예) 0~80km/h 부드럽게, 100km/h 이상 단단하게. 올라갈 때와 내려갈 때 기준을 10~15km/h 다르게 둔다(경계에서 왔다 갔다 방지).
- 코너: 횡가속도가 기준(예 0.25g)을 0.3초 넘으면 단단하게, 기준 아래로 2~3초 유지되면 원래대로.
- 공통: 한 번 바꾸면 최소 3초 유지, 분당 전환 횟수 상한. 순정 시스템이 원래 운전자 버튼 조작 빈도를 가정하므로 잦은 전환은 피한다.
- 단계가 2~3개뿐이라 "가변"은 계단식이다. 연속적으로 변하는 느낌은 나지 않는다.

## 안전 설계

- 이 방식은 순정 ECS ECU의 실시간 제어를 그대로 둔다. 바꾸는 것은 운전자가 설정 화면에서 누를 수 있는 값뿐이다.
- 자동 전환은 사용자가 커스텀 모드를 직접 골랐을 때만 동작한다. 모듈이 드라이브 모드 자체를 바꾸지는 않는다.
- 모듈·휴대폰이 죽으면 마지막 단계에 머문다(순정 범위 안의 값). 재시동하면 차가 스스로 기본 모드로 돌아간다.
- 응답 피드백이 예상과 다르거나 고장 상태가 보이면 자동 전환을 멈추고 더 보내지 않는다.
- 후진·주차 중에는 보내지 않는다.
- 남는 위험: 코너 도중 단계가 바뀌면 차 거동이 약간 달라질 수 있다(순정 스마트 모드도 하는 일이지만 순정은 ECU가 시점을 고른다).
  코너 규칙은 "코너 진입 전에 단단하게, 코너가 끝난 뒤에 풀기" 쪽으로만 동작하게 한다.

## 현장 확인 계획 (한 번에 묶음, 정차 상태)

읽기 전용(차량 명령 없음)
1. 드라이브 모드 → 커스텀 설정 화면 사진: 항목과 선택지.
2. 노트북으로 로그를 받는 동안 사용자가 순정 화면에서 서스펜션 항목을 단계별로 바꾼다.
   → `setIndividualDriveMode device/mode` 값, 응답 프레임, 걸리는 시간을 얻는다.
3. 드라이브 모드 버튼으로 컴포트→스포츠→커스텀을 돌려 모드 값(커스텀의 byte 값 포함)을 기록한다.

송신 시험(**사용자 승인 후**, 주차 브레이크·속도 0을 로그로 확인한 뒤)
4. 2번에서 얻은 값 그대로 `setIndividualDriveMode`를 한 번 호출해 화면과 응답이 순정 조작과 같은지 본다.
5. 같으면 시험 모듈을 설치하고 저속 주행에서 속도 규칙만 먼저 확인한다(별도 승인).

## 만들 순서

1. (현장 1~3 뒤) 값이 확정되면 `core/`에 규칙 엔진과 프로토콜 + 단위 시험. 차량 없이 PC에서 검증.
2. 차량 모듈: 로그 읽기 + 규칙 + 송신부(송신은 기본 꺼짐, 모의 모드 포함).
3. 휴대폰 앱: 설정 화면, 횡가속도 측정, 연결.
4. 현장 4~5.

빌드 방식과 도구는 k8-ambient-sync의 것(`tools/build_api19_dex.py`, `build_nemesis_relay.py`, `build_phone_relay.py`)을 본떠 이 저장소에 따로 둔다.
ESP32는 이 경로에 필요 없다.

## 2026-11-15 저녁: 실차 읽기 전용 확인 + 요구 변경

실차 로그(정차, `getSpeed_KMHUnit() = 0.0`, 읽기만 함. 원본은 `private/captures/`)
- 커스텀 설정 화면에 들어갈 때 순정 앱이 `requestNewMyDriveMode` data `01 01`을 보낸다 → 패킷 `SYS_DRV_NEW_MY_DRV_MODE_C_REQ`(0x18a), Binder 트랜잭션 0x3b.
  순정 앱 코드상 data는 `[읽기면 1 / 쓰기면 0, 번호]`로 보인다(추정). K8은 0x13e·0x187이 아니라 **이 0x18a 계열**을 쓸 가능성이 높다.
- 서스펜션 값을 바꾸는 순간의 줄은 아직 못 받았다(사용자가 화면에서 바꿔 줘야 함).
- 사용자 확인: 서스펜션 선택지는 **에코 / 스포츠 2개**.
- 헤드유닛에는 가속도·자이로 센서가 없다(`dumpsys sensorservice` 목록이 빔). 차량 단독 코너 감지는 차량 데이터(N 모드 횡G 요청이 통하는지)에 달려 있다.

요구 변경(사용자)
- 판단·전환은 휴대폰 블루투스 연동 없이 **차량 NEMESIS 모듈 단독**으로 한다(반응 속도).
- 설정은 차량 화면에서도, 휴대폰에서도 바꿀 수 있게 한다. 휴대폰은 설정 전용.

### 실차 확정 값 (2026-11-15 19:39~19:41, 순정 화면 조작을 로그로 읽음)

K8 커스텀 화면 항목: 파워트레인(ECO/SPORT), 스티어링(NORMAL/SPORT), 서스펜션(2개, 낮은 쪽/SPORT).

| 조작 | 호출 | 마이컴 프레임 | 상태 응답 |
|---|---|---|---|
| 서스펜션 낮은 쪽 | `setIndividualDriveMode(1, 0)` | `ff 8a 01 01 01 3e 00 03 01 00 48` | feedback[1]=2 |
| 서스펜션 SPORT | `setIndividualDriveMode(1, 1)` | `ff 8a 01 01 01 3e 00 03 01 01 49` | feedback[1]=5 |
| 스티어링 NORMAL | `setIndividualDriveMode(2, 0)` | `… 3e 00 03 02 00 4b` | feedback[2]=2 |
| 스티어링 SPORT | `setIndividualDriveMode(2, 1)` | `… 3e 00 03 02 01 4a` | feedback[2]=5 |

- 응답은 `SYS_DRIVE_MODE_DATA_M_RESP` 18바이트. byte 2 = 현재 드라이브 모드(02 에코, 03 스포츠, 06 스마트, 00 전환 중/그 외),
  byte 4 = 항목 지원 비트(0x60 → 항목 1, 2), byte 6·7 = 항목별 설정값을 4비트씩(`0x45 0x52` → [0]=4, [1]=5, [2]=5, [3]=2).
  로그에는 `mIndividualModeFeedback: [0] 4 [1] 5 …`로도 풀려 찍힌다 → 차량 모듈은 이 줄로 결과를 확인한다.
- 요청에서 응답까지 0.1~0.3초.
- 드라이브 모드를 에코↔스포츠로 바꿔도 feedback 값은 그대로다 → 커스텀 모드용 저장값이다. 실제 감쇠가 커스텀 모드에서만 따라가는지는 미확인.
- 커스텀 모드일 때 byte 2 값은 아직 못 봤다.
- `requestNewMyDriveMode 01 01`은 커스텀 화면 진입 때 나가는 조회로 보이며 항목 변경과 무관하다.
- 우리 모듈이 같은 호출을 했을 때 받아들여지는지(송신 시험)는 아직 안 했다.

### 송신 시험 결과 (2026-11-15 19:42, 사용자 승인, 속도 0.0 확인 후)

- 서비스 이름은 `com.hkmc.micom.system`(인터페이스 `com.hkmc.micom.ISystemService`)이다. 앞의 `com.hkmc.Service.SYSTEM_SERVICE`는 틀렸다.
- **서스펜션 송신: 통함.** adb 셸(uid 2000)에서 `service call com.hkmc.micom.system 48 i32 1 i32 0` → 순정과 같은 프레임(`… 3e 00 03 01 00 48`),
  0.2초 뒤 feedback[1]=2. 이어서 `… i32 1 i32 1` → feedback[1]=5(SPORT 복귀). 권한 오류 없음. 모듈 설치 없이 명령 한 줄씩으로 했다.
- 읽기 `service call com.hkmc.micom.system 49`(getIndividualDriveMode)도 된다 → 로그 없이 현재 값을 직접 읽을 수 있다.
- **N 모드 데이터 요청: 응답 없음.** `requestNModeData(1)`(프레임 `… 41 00 02 01 36`) 뒤 10초간 `SYS_G_FORCE…` 등 수신 0건, 원시 마이컴 프레임에도 없음.
  `requestNModeData(0)`을 보내고 종료. 다른 값은 시도하지 않았다. → 차량 횡G 통로는 K8에서 쓸 수 없다.
- 헤드유닛에서 얻을 수 있는 코너 신호 후보: 내비 GPS 방위(`GisUtil setGPSData … HEADING=<도>`, 약 1초 간격, 1도 단위).
  속도 × 방위 변화율로 횡가속도를 추정할 수 있지만 1~2초 늦다. 주행 로그로 쓸 만한지 확인해야 한다.
- 남은 미확인: 커스텀 모드일 때 `SYS_DRIVE_MODE_DATA_M_RESP` byte 2 값, 서스펜션 설정이 커스텀 모드에서만 실제 적용되는지, 주행 중 변경 허용 여부.

## 차량 횡G 출처: 헤드유닛 GPS 모듈 센서 (2026-11-15 19:50~, 읽기 전용)

- 헤드유닛 GPS(u-blox ADR, `ro.kernel.android.gps=ttyTCC3`)의 수신 데이터는 커널 `dup_ldisc`가 `/dev/ttyGPS0~2`(dupuart)로 복제한다.
  ttyGPS1은 내비가 쓰고, ttyGPS2는 부팅 뒤 아무도 열지 않았다 → 여기를 읽으면 원본을 빼앗지 않는다.
- 복제 포트에는 쓰기 경로(`du_pops_start_tx`)가 있으므로 반드시 에코를 끈 원시 모드로 연다(숨은 API `android.hardware.SerialPort.open`). 절대 쓰지 않는다.
  권한: `/dev/ttyGPS*`는 system:gps 0660 → `nemesis root 1000`(system)으로 실행.
- 형식(u-blox 표준 아님): 0x81 시작, 0x82 끝, 0x80 n = 0x80|n. 첫 두 바이트가 종류. 10Hz 메시지:
  - `70-13` 단축 자이로: 창(100ms)마다 원시값 합(int32 @14)과 샘플 수(int32 @18, 19~21개 ≈ 200Hz). 정차 중 평균 약 34 LSB(영점 편차).
  - `70-14` 3축 가속도: 축마다 {합, 샘플 수, 누적, 시각}. 정차 중 2번 축이 16384 LSB ≈ 1g(중력) → 16384 LSB/g로 보인다.
  - 헤더 @4 = 헤드유닛 ms 시각. 다른 종류(30-02, 70-32/33 등)는 위치 해(위치 정보 포함, 기록·출력하지 않음).
- 속도: BCM `getSpeed_KMHUnit()`(Binder `com.hkmc.micom.bcm` 트랜잭션 0x2f, 읽기 전용 getter)를 10Hz로 직접 읽을 수 있다.
- 남은 일: 자이로 축이 요(yaw)인지, 단위(LSB per deg/s)와 부호 → 주행 기록(`probe/DriveLog`)을 내비 GPS 방위 변화와 비교해 정한다.
  횡G = 속도 × 요레이트. 가속도계 측면 축도 같은 기록으로 비교한다.
- 정차 2분 기록(19:58~20:00): 자이로 창 평균 34.0 LSB, 표준편차 1.95(창 1225개). 가속도 축 평균 0.023 / 1.006 / 0.006 g.
  주행 기록은 아직 없다(사용자가 오늘은 주행 불가). 기록기는 중지했고 헤드유닛의 임시 파일은 모두 지웠다.
  다음 방문: `probe/DriveLog`를 다시 올려 5~10분 주행(좌우 회전 포함) 기록 → 단위·부호 결정.

## 클러스터 스포츠 테마 (2026-11-20, 0.4.5 실차 시험)

- 호출(`IUSMService`, 인터페이스 `com.hkmc.usm.IUSMService`):
  - 현재 테마 읽기: `getCluster_ThemeStatusNew()`, Binder 트랜잭션 `0x22b` (읽기 전용).
  - 테마 설정: `setCluster_ThemeStatusNew(int)`, 트랜잭션 `0xc4`, 값 `1..4`만 허용.
  - 드라이브 모드 연동 여부 읽기: `getCluster_ThemeAutoSetStatus()`, 트랜잭션 `0x1ac` (읽기 전용, 설정 호출 안 함).
- 로그캣 수신(`logcat` 필터에 `USMService:V`, `ThemeSettingService:D` 추가):
  - `USMService`: `Cluster_ThemeStatusNew: N`
  - `ThemeSettingService`: `nThemeStatusNew : N` (`onClusterETCStatusReceived` 줄)
- 값 대응: `1..4 = 테마 A..D`. 실차에서 순정 메뉴로 B·A·C를 고를 때 `2`·`1`·`3`이 찍혀 확인했다(D=`4`는 순서상 추정).
  순정 메뉴의 선택은 MICOM `USM_CLU_SET_ETC_C_REQ`(0x1124) `01 <값>`으로 나가고, 모듈의 `setCluster_ThemeStatusNew`도 같은 패킷을 만든다.
- 순정 '드라이브 모드 연동'(`ThemeAutoSetStatus`/`nThemeAutoSetStatus`): `1` 꺼짐, `2` 켜짐. 켜져 있으면 테마 값이 `15`로 보고되고 차가 모드별 화면을 직접 정한다.
  **이 기능은 연동이 꺼져 있어야 작동한다.** 모듈은 연동 켜짐(`2`)을 보면 전환하지 않고 상태를 `cluster=link_on`으로 알린다(0.4.6). 순정 메뉴에서 테마를 직접 고르면 연동이 꺼진다.
- 실차 시험(2026-11-20, 정차):
  - 0.4.5, 연동 꺼짐, 드라이브 모드 **스포츠**: 모듈이 테마 C(`3`)를 두 번 보냈지만 테마가 그대로여서 `HALT cluster: no feedback twice`로 멈췄다.
  - 같은 명령을 **에코**에서 `service call`로 한 번 보냈을 때는 바로 `3`으로 바뀌었고, `1`로 되돌렸다.
  - 즉 순정 스포츠 모드 중에는 클러스터가 테마 변경을 받지 않는 것으로 보인다. 마이 드라이브(`0x06`)에서의 동작은 아직 확인 전이다.
- 동작 규칙(`ClusterThemeController`):
  - 순정 스포츠 모드(`0x03`)이거나 마이 드라이브에서 서스펜션·핸들·엔진 중 하나라도 피드백상 스포츠면 고른 테마로 바꾼다. 기본값은 꺼짐(`clusterOn=0`, `clusterTheme=1`).
  - 스포츠 상태가 끝나고 **5초** 연속 유지되면 원래 테마로 복귀한다(중간에 다시 스포츠가 되면 타이머 초기화).
  - 스포츠 중이거나 복귀 대기 중에 운전자가 테마를 직접 바꾸면 덮어쓰지 않고 이번 전환을 취소한다.
  - 응답이 3초 안에 안 맞으면 1회 재시도하고, **2회 실패**하면 클러스터 전환만 멈춘다(`halted`, "정지 해제"로 복구).
  - 재시작 시 `state.txt`의 `clusterOrig`를 읽어 스포츠 상태가 끝나 있으면 원래 테마로 복귀한다.
- 첫 현장 확인(주차 상태):
  1. 모듈 상태(`STATUS` / 앱 상태 줄)에서 `clusterTheme`과 `clusterAutoSet`이 읽히는지 확인한다.
  2. 옵션을 켜고 드라이브 모드를 **에코 → 스포츠 → 에코**로 한 번 전환해 고른 테마로 바뀌었다가 5초 뒤 원래 테마로 돌아오는지 확인한다.
